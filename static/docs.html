BUILD-A-WALLET DOCUMENTATION

One platform. Two audiences.

NON-HUMAN is policy-controlled wallet infrastructure for autonomous agents. HUMAN is a guided wallet-design experience for people who want to define and control their own wallet blueprint.

Canonical endpoint: https://buildawallet.xyz. Check /machine/info for the separately deployed paid data Worker. Agent signing and the /v1 API are not deployed; MCP is available only on the Python origin.

NON-HUMAN: agentic wallet infrastructure

Use this mode when software agents, autonomous services, treasury bots, machine-commerce systems, or agent fleets need crypto wallets and transaction capabilities without unrestricted private-key authority.

Core flow

Agent → Scoped credential → Wallet authority → Policy evaluation
      → Human/operator approval boundary → Chain adapter → Receipt

Controls planned for the agent service

  • Per-transaction USD limits
  • Daily spending budgets
  • Allowed assets and destinations
  • Approval thresholds
  • Wallet freeze and credential revocation
  • Authority expiration
  • Server-side USD valuation
  • Audit events and execution status

Paid mainnet wallet data

The separately deployed machine Worker offers read-only native balance snapshots. Check /machine/info for availability before using it. It does not create wallets, sign transactions, or control funds.

GET endpointResponsePrice
/machine/wallet?address=0x...Base ETH balance, transaction count and block$0.01 USDC
/machine/solana-wallet?address=...Solana SOL balance and slot$0.01 USDC

A valid unpaid request returns HTTP 402 with x402 payment options. A compatible client pays with USDC on Base or Solana mainnet, then retries with the payment payload. Base payments go to 0xBcCA6AED433d9020C50D44560F9679F1B5eB511d; Solana payments go to Ew8mbrKwD6LGaSX28a6XGmXqeQSs2hykRibjXVhftTRC. Invalid addresses return 400, unavailable RPC or configuration returns 503, and rate limited calls return 429.

The RPC snapshot is fetched before an x402 challenge, so an RPC failure does not create a payable response. Real payment settlement still requires a post-deployment paid transaction check on each rail.

HUMAN: user-controlled wallet builder

The HUMAN experience is a guided design tool for people. Users choose assets, networks, custody preferences, security controls, features, privacy, interface style, and other wallet characteristics. The result is a visual blueprint and shareable configuration. The live balance view can connect an existing external wallet and read its Base or Solana native balance. Sending, generated APK wallets and subscription access are not released.

  1. Choose assets and networks.
  2. Select custody, backup and recovery preferences.
  3. Choose security and approval controls.
  4. Add product features and UI preferences.
  5. Review the live preview and blueprint.
  6. Save or share the resulting wallet design.

The HUMAN builder is available at /human. Studio can download the blueprint as JSON; it does not package an Android app.

Authentication

The local Agent Protocol prototype uses scoped bearer credentials. It is not deployed on the public site. In that prototype, bootstrap credentials are created with a deployment secret, tokens are shown once and stored server-side only as hashes.

Authorization: Bearer baw_...

In the local prototype, agent credentials can create/read wallets and request transactions. Operator credentials are separate and can approve, execute, freeze wallets, revoke credentials and inspect audit history.

Policy objects

{
  "max_transaction_usd": 25,
  "daily_spend_limit_usd": 50,
  "require_human_approval_above_usd": 10,
  "allowed_actions": ["balance","receive","send"],
  "allowed_assets": ["ETH"],
  "allowed_destinations": [],
  "deny_unknown_destinations": true,
  "expires_in_seconds": 3600
}

USD values used for enforcement are calculated server-side. Caller-provided USD values are not trusted for policy decisions.

Wallets

The local prototype models task, session, budget and other wallet authorities. Its key generation code is not part of the public site or a production signing service.

Create

POST /v1/wallets
Content-Type: application/json
Authorization: Bearer <agent token>

{
  "chain":"base",
  "wallet_type":"task",
  "purpose":"checkout-agent",
  "policy": { ... }
}

Read balance

GET /v1/wallets/{wallet_id}/balance

Freeze

POST /v1/wallets/{wallet_id}/freeze

Transactions

In the local prototype, money-moving requests require an Idempotency-Key. Reusing the same key with a different body returns conflict instead of silently creating a second transaction.

POST /v1/wallets/{wallet_id}/transactions
Idempotency-Key: checkout-8742

{
  "asset":"ETH",
  "amount":0.001,
  "destination":"0x..."
}

Possible request states include denied, approval_required, and ready_for_signing. Execution is unavailable on the public server. A local prototype has an operator scope and a broadcast safety switch.

MCP

The Python container offers read-only preview discovery through MCP Streamable HTTP at /mcp. This route is not part of the Cloudflare Pages and Worker deployment. MCP is intended as a machine-native discovery and tool interface while REST/OpenAPI remains the canonical policy/execution surface.

Agents should never receive separate privileged signing authority through MCP. MCP tools must inherit the same policy and operator boundaries as REST.

Security model

The public site does not generate or store signing keys. The following controls are modeled in local prototypes only:

  • Agent and operator authority are separated.
  • Credentials are revocable.
  • Wallets can be frozen.
  • Execution state is locked to reduce duplicate broadcasts.
  • USD policy enforcement uses server-owned pricing.
  • Broadcast is disabled unless the exact mainnet safety switch is enabled.
  • Encrypted local custody is not represented as HSM/MPC custody.
Production deployments should use dedicated secret management/KMS/HSM controls, HA persistence, rate limiting, tenant boundaries, monitoring and incident-response procedures.

Production checklist

  • Use stable private RPC endpoints for every enabled network.
  • Replace development credentials before funding wallets.
  • Move persistence to a production HA database before high concurrency.
  • Move signing secrets to hardened secret-management infrastructure.
  • Configure rate limits, request logging and alerting.
  • Define tenant/org boundaries for operator authority.
  • Keep broadcast disabled until controlled validation is complete.
  • Review token contract/mint bindings before enabling arbitrary token sends.
