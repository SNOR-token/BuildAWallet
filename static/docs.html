BUILD-A-WALLET DOCUMENTATION

One platform. Two audiences.

NON-HUMAN is policy-controlled wallet infrastructure for autonomous agents. HUMAN is a guided wallet-design experience for people who want to define and control their own wallet blueprint.

Canonical endpoint: https://buildawallet.xyz. The agent API and MCP endpoints described below are implementation plans and local prototypes; they are not available as production mainnet services.

NON-HUMAN: agentic wallet infrastructure

Use this mode when software agents, autonomous services, treasury bots, machine-commerce systems, or agent fleets need crypto wallets and transaction capabilities without unrestricted private-key authority.

Core flow

Agent → Scoped credential → Wallet authority → Policy evaluation
      → Human/operator approval boundary → Chain adapter → Receipt

What the platform enforces

  • Per-transaction USD limits
  • Daily spending budgets
  • Allowed assets and destinations
  • Approval thresholds
  • Wallet freeze and credential revocation
  • Authority expiration
  • Server-side USD valuation
  • Audit events and execution status

HUMAN: user-controlled wallet builder

The HUMAN experience is a guided design tool for people. Users choose assets, networks, custody preferences, security controls, features, privacy, interface style, and other wallet characteristics. The result is a visual blueprint and shareable configuration.

  1. Choose assets and networks.
  2. Select custody, backup and recovery preferences.
  3. Choose security and approval controls.
  4. Add product features and UI preferences.
  5. Review the live preview and blueprint.
  6. Save or share the resulting wallet design.

The HUMAN builder is available at /human.

Authentication

Agent Protocol requests use scoped bearer credentials. Bootstrap credentials are created with the deployment bootstrap secret. Tokens are shown once and stored server-side only as hashes.

Authorization: Bearer baw_...

Agent credentials can create/read wallets and request transactions. Operator credentials are separate and can approve, execute, freeze wallets, revoke credentials and inspect audit history.

Policy objects

{
  "max_transaction_usd": 25,
  "daily_spend_limit_usd": 50,
  "require_human_approval_above_usd": 10,
  "allowed_actions": ["balance","receive","send"],
  "allowed_assets": ["ETH"],
  "allowed_destinations": [],
  "deny_unknown_destinations": true,
  "expires_in_seconds": 3600
}

USD values used for enforcement are calculated server-side. Caller-provided USD values are not trusted for policy decisions.

Wallets

Supported wallet authority types include persistent, task, session, budget, escrow and multisig descriptors. Cryptographic wallet generation is available for EVM, Solana, Bitcoin and Litecoin families.

Create

POST /v1/wallets
Content-Type: application/json
Authorization: Bearer <agent token>

{
  "chain":"base",
  "wallet_type":"task",
  "purpose":"checkout-agent",
  "policy": { ... }
}

Read balance

GET /v1/wallets/{wallet_id}/balance

Freeze

POST /v1/wallets/{wallet_id}/freeze

Transactions

Money-moving requests require an Idempotency-Key. Reusing the same key with a different body returns conflict instead of silently creating a second transaction.

POST /v1/wallets/{wallet_id}/transactions
Idempotency-Key: checkout-8742

{
  "asset":"ETH",
  "amount":0.001,
  "destination":"0x..."
}

Possible request states include denied, approval_required, and ready_for_signing. Execution is operator-scoped and protected by a mainnet broadcast safety switch.

MCP

Build-a-Wallet exposes MCP Streamable HTTP at https://buildawallet.xyz/mcp. MCP is intended as a machine-native discovery and tool interface while REST/OpenAPI remains the canonical policy/execution surface.

Agents should never receive separate privileged signing authority through MCP. MCP tools must inherit the same policy and operator boundaries as REST.

Security model

  • Private keys are never returned through the HTTP API.
  • Agent and operator authority are separated.
  • Credentials are revocable.
  • Wallets can be frozen.
  • Execution state is locked to reduce duplicate broadcasts.
  • USD policy enforcement uses server-owned pricing.
  • Broadcast is disabled unless the exact mainnet safety switch is enabled.
  • Encrypted local custody is not represented as HSM/MPC custody.
Production deployments should use dedicated secret management/KMS/HSM controls, HA persistence, rate limiting, tenant boundaries, monitoring and incident-response procedures.

Production checklist

  • Use stable private RPC endpoints for every enabled network.
  • Replace development credentials before funding wallets.
  • Move persistence to a production HA database before high concurrency.
  • Move signing secrets to hardened secret-management infrastructure.
  • Configure rate limits, request logging and alerting.
  • Define tenant/org boundaries for operator authority.
  • Keep broadcast disabled until controlled validation is complete.
  • Review token contract/mint bindings before enabling arbitrary token sends.
